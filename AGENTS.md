# shelvd — conventions for contributors and coding agents

Django backend (`backend/`, API via Django Ninja), Vue 3 + TypeScript SPA (`frontend/`), one hardened Docker image. Read this before changing structure; `README.md` has setup and commands.

## Commands

The `justfile` holds every command; CI (`.github/workflows/build.yaml`) and the VS Code tasks (`.vscode/tasks.json`) only call its recipes. `just` lists them; `docs/development.md` has setup and the GitHub configuration.
- `just dev-backend` + `just dev-frontend` (task **Dev: start all**): Django :8000 (`BACKEND_PORT`) + Vite :8080 (`APP_PORT`, same as Docker) → http://localhost:8080. Both read the repo's `.env`.
- `just check` runs everything CI runs. It must pass before a push; `just check-changed` before a commit. A new check goes into a recipe, never as an extra command into a workflow.
- `just api-types` after any API change (schema → `frontend/openapi.json` → `frontend/src/api/schema.d.ts`); commit both files.
- `just migrations` after model changes; commit the migrations.
- Frontend package manager is **pnpm** only; its version lives only in `packageManager` (Dockerfile and CI read it). Backend dependencies via `uv add` / `uv add --dev`.
- Pull request titles are Conventional Commits (`feat: …`, `fix: …`, `deps: …`); release-please makes releases from them.
- Not updated by Dependabot, bump by hand: `TRIVY_IMAGE` and `POSTGRES_IMAGE` in `build.yaml` (Postgres together with `compose.yml`), actionlint and zizmor in the justfile, `rust-just` in the workflows, `.pre-commit-config.yaml`, and pnpm's `packageManager` if Dependabot leaves it alone.

## Backend rules

- Apps live in `backend/apps/<name>/` (`name = "apps.<name>"`, `label = "<name>"`), registered in `INSTALLED_APPS`.
- **No monolithic modules.** `models/`, `admin/`, `api/`, `schemas/`, `services/`, `tests/` are packages with one file per model/resource; `__init__.py` re-exports explicitly. Relations use string references (`"app.Model"`).
- **Every model inherits `apps.core.models.UUIDModel` or `TimeStampedModel`** (UUID primary key). `manage.py check` fails (`core.E001`) otherwise. Order queries explicitly.
- Business logic goes in `services/` (writes) and `selectors/` (reusable reads), not in API views or models' `save()`.
- No URL may contain words content blockers filter (`track`, `tracking`, `analytics`, `ads`, `banner`, `pixel`, `beacon` …): frontend source paths (they are URLs in dev), chunk/component names, routes and API paths. Users with uBlock/EasyPrivacy would get "failed to load module" or blocked API calls. That's why the tracking feature lives at `/api/watchlist` and `src/features/watchlist`.
- API: under `/api/`, no trailing slashes, session auth + CSRF, UUIDs in paths. `/api/health` stays unauthenticated and exactly at that path.
- Configuration only via environment variables read through `config/env.py`; every new variable gets a commented entry in `.env.example`.
- mypy runs in strict mode; type all new code. Coverage must stay ≥ 90 %.
- shelvd is `AGPL-3.0-or-later` (`LICENSE`). Dependencies must be compatible with it: no SSPL, no GPL-2.0-only (CI license check; GPL-3.0, AGPL-3.0, LGPL, permissive are fine). The app offers its source (AGPL §13) via `src/lib/source.ts` → `SourceLink` (login, public pages) and the user menu; keep those links when changing these pages.

## Frontend rules

- Feature folders: `src/features/<feature>/{components,composables,views}`, routes in `src/router/routes/<feature>.ts`.
- Server state via TanStack Query composables around the typed `api` client (`src/api/client.ts`); Pinia only for client state.
- Bundle budgets (`scripts/check-size.mjs`, limits in `package.json` → `sizeBudget`): **initial JS** = what the first start loads (entry + `index.html` modulepreloads) is kept tight; **total JS** covers every chunk. Big things that aren't needed at startup (dialogs, scanner, rarely used pages) go behind a dynamic `import()` so they count only towards the total.
- UI components from shadcn-vue (`pnpm dlx shadcn-vue@latest add <component>`) in `src/components/ui/` — vendored, edit freely.
- Tailwind for styling. No inline `<script>` and no remote scripts: the CSP only allows scripts from our origin.
- Never edit `src/api/schema.d.ts` by hand.

## Domain (shelvd: game collection, later DVD/Blu-ray too)

- `catalog` — app-wide, shared by everyone, independent of who owns what: `Platform`, `Company`, `Genre`, `Series`, `Work` (the game/film itself, `media_type`; how it's played from IGDB: `game_modes`, `perspectives`, `languages` – IGDB's English names –, several `series` and `franchises` – a franchise is the brand ("Mario"), a series one line of games in it ("Super Mario"); from IGDB: collections → series, franchises → franchises), `Release` (work × platform × region × edition, with `players_offline`/`players_online`, cover and a release date with precision: `release_precision` day…year/window/tba, `release_date` = first day of the period, `sort_date`/`is_released` derived in `models/dates.py`), `Barcode` (confirmed GTIN – or an article number from Code 128/39, matched against `product_code` too – → release). Companies (publisher on the release, developers on the work), genres, franchises and series (several per work) are *terms*: forms pick them with `TermPicker` (suggestions from `GET /api/catalog/<kind>?q=`, existing ones sent as `{id}`, new ones as `{name}`); `services/terms` resolves names case-insensitively, so never `get_or_create(name=…)` them directly. A series may belong to a franchise (`Series.franchise`, picked on the series' edit page, taken from Wikidata's „media franchise“ (P8345) when that franchise is in the catalog; the franchise's page lists its series as `parts`). Companies, genres, franchises and series have a description per language (`descriptions` {"de": …, "en": …}; the API's `description` is the reader's language, else another, `description_language` says which); Wikipedia takes every language's article at once; it describes companies, series and franchises (a „video game series“ is first of all a series, a „media franchise“ or „video game franchise“ a franchise; a name that finds nothing fitting is searched in English too, then through what points to it: games' „part of the series“ (P179), series' and games' „media franchise“ (P8345)). Companies also carry details (founded/dissolved year, ISO country, seat, website, `parent` → `subsidiaries`), filled by hand or when a Wikipedia description is taken (Wikidata facts; parent and subsidiaries are only linked to companies already in the catalog, never created). Each kind has its pages (`/companies`, `/genres`, `/franchises`, `/series` – an overview like the platforms page: table or tiles (`ui.termLayout`), A–Z by initial or most used (`ui.termSort`), each entry with its logo or a tinted initial (`TermMark`) and what it is (a company's country and year, else the start of its description: `summary`) –, then `/<kind>/<id>` with `/edit` and `/merge`; routes in `router/routes/terms.ts`, the kind in `meta.kind`) and API (`api/terms.py`: list, detail, rename – 409 on a clash, merge into another, delete); names are unique regardless of case. Detail blocks link term values to these pages (`link` in `ITEM_FIELDS`). The edition is free text with suggestions (`EditionInput`, `GET /api/catalog/editions`), no entity. **Only admins (`is_staff`) change the catalog** (`accounts.selectors.require_admin`; per entry `catalog.selectors.review.can_edit`, exposed as `can_edit` on games and releases). Library editors (`collection.services.access.can_contribute`) may still bring games in: taken from IGDB they are reviewed; entered by hand, a barcode assigned or brought in by an importer add-on they stay `review_status=pending` (`created_by`) – usable right away, badged „Ungeprüft“ – until an admin approves them in the review queue (`/catalog/review`); the creator may edit their own pending entries until then. Library pages never change the catalog. The concept is in `docs/concept-permissions.md`. Pictures of terms and platforms (logos, photos) lose a plain white background when stored – logos a plain black one too (an SVG its full-size backdrop rectangle), photos never (`core/services/images.clear_background`, in `store_icon`; a picture of nothing but background stays) and get their tone measured once by their pixels – an SVG drawn with resvg (`resvg-py`) first – (`catalog/services/tones.note_tones` → `image_tone`/`photo_tone`: black/dark/white/light); pages wrap them in `ToneBox` with the same `spotlight` behind every picture: a one-colour logo is inverted where it would vanish, anything in colour and every photo gets a fine rim – never a box of its own colour. Platforms are listed at `/catalog/platforms`; each has its page `/platforms/<id>` like a company's (logo `image` and a photo of the device `photo` – the hero shows the photo, the logo above the figures –, `descriptions` per language, `generation`, release year and `discontinued`, manufacturer – free text, linked to the catalog company of that name –, `predecessors` → `successors`, its games via `GET /api/catalog/platforms/<id>/games`) and is edited at `/catalog/platforms/<id>/edit`. Wikipedia and IGDB describe platforms like companies (kind `platforms`): a platform fills short name (Kürzel), manufacturer and year only where empty – badges, grouping and sorting use them –, sets generation and end of production, and links predecessors/successors already in the catalog (by id, name, short name or name without the maker). Its badge: own colour (else the manufacturer's) and a neutral symbol (`lib/platformIcons.ts`) or an icon – uploaded or the platform's small logo taken from a source (`/platforms/<id>/image`: every logo, small logo and photo of the linked entries – and any picture found on Wikimedia Commons (`GET /api/catalog/commons-images?q=`) –, each takable as the page's logo, photo or the badge's icon; raster pictures over 2 MB are scaled down before they're kept; taken as an icon, a raster picture loses a plain light background and is cut to the device (`core/services/images.make_icon`), so a photo of the device makes an icon). Most source icons are small colour illustrations and stay as they are; a dark mark in one colour (a black glyph like the Switch's) is detected when the icon is saved (`core/services/images.is_dark_mark` → `Platform.icon_dark`) and shown inverted in dark mode. Picture boxes are grids with one `minmax(0,1fr)` cell (`grid-cols-1 grid-rows-1`) – with an auto row, `max-h-full` doesn't hold a tall photo. `/catalog/platforms` lists them as a table or as tiles with the photo (`ui.platformLayout`). Logos are fine there, as for companies. SVGs are checked for scripts and links in `core/services/images.store_icon`.
- `collection` — per library: `Library` (+ `LibraryMember` with role viewer/editor; owner can do everything), `Location` (free tree: room › shelf › box), `Person` (owners of copies and borrowers, no account needed), `Item` (one copy; status only owned/sold; it may differ from its release in title, cover, edition, region and release date – `*_override`, empty = as the release, never copied from the catalog. `Item.shown` is the release with them applied: `ItemOut.release`, lists, sorting, grouping and filters use it, `overrides` names what differs; reset per field or `POST …/items/<id>/reset`), `Loan`, `Overview` (a user's saved view: nesting `group_by` into folders, `section` – one grouping field whose groups head collapsible sections of the item list (`/items?section=`, with `sections` in the response) –, filters, sort, layout). Access checks go through `services/access.get_library(user, id, need=…)` — 404 for invisible, 403 for not allowed. Viewers never see people's contact details or money (price, value, total value) and loans only as the owner sets `Library.viewer_loans` (hidden / status only); `services/visibility.py` blanks them and drops grouping/sorting/filtering by those fields. The loans list is for editors.
- **Field keys are paths** – object and field – and the same everywhere: backend grouping (`selectors/grouping.FIELDS`), sorting (`selectors/sorting.SORT_KEYS`), filter conditions (`selectors/conditions.py`), the frontend's field registry (`lib/itemFields.ts`), saved views and the URL. Objects: `game.*` (Spiel), `release.*`, `platform.*`, `publisher.*` (Ausgabe), `copy.*`, `location.*`, `owner.*`, `loan.*` (Exemplar). Examples: `platform.name`, `location.kind`, `release.number`, `copy.value`. No aliases for old names – rename with a data migration (see `collection/migrations/0008_path_keys.py`). `/tree` and `/items?filter=field:key` share the grouping extractors, so tree and list never disagree. A new field = one entry in each backend list it applies to + `ITEM_FIELDS` (+ `GROUP_FIELDS` in `frontend/src/api/types.ts` if it groups) + an `itemFields.<object>.<field>` label in both locales.
- `tracking` (API `/api/watchlist`, frontend `features/watchlist`) — a person's watched / pre-ordered / bought-but-not-arrived releases (`Tracking`), not part of any library; an optional target library (needs editing rights there) lets its members see the entry read-only – without price, shop, order date or notes of other people's entries. `take-over` turns it into an `Item` once it arrives. In the UI the section is **Demnächst** (en: Upcoming); an entry has no name of its own (no "Vormerkung"), it's the game. One entry = one page (`tracking-edit`) that holds everything: status, release date (catalog), purchase, optional library, removing; the list row opens it, the row's ⋮ and the game page's chip only lead there or change the status. Links to a game from Upcoming use the library you're in – never switch libraries silently.
- `sharing` — personal lists and public read-only links (`/api/public/...`, no auth; never expose people, places, prices or notes there).
- `providers` — external sources behind `sources/base.py` protocols: metadata (IGDB; Wikipedia only completes games – `catalog=False` – with texts in the UI language, and describes companies and series via `DescriptionSource` – ranked by kind, exact name and article, retrying a company's name without legal form or spaces; a company entry without an article still gives its facts –, taking their logo from Wikimedia Commons along if wanted; IGDB describes companies too – English text, country, founding year, website, parent – and platforms (text of the platform or its original model, abbreviation, generation, year); both describe platforms (kind `platforms`, see `catalog`),, and a name it finds nothing for is searched without „Studio“/„Games“ but never counted sure; `sources/names.py` holds the shared name rules. Every picture of the entries a term or platform is linked to – all of a Wikidata entry's logos, older ones too, small logos, a platform's photos, and IGDB's – can be chosen at `/<kind>/<id>/image`, as encrypted tokens with previews through the server like covers), facts (HowLongToBeat play times, OpenCritic scores → cached per game in `catalog.WorkFact`, refreshed when older than the integration's max age: on opening a game, by `run_scheduler`, or forced); IGDB's own time to beat and page address are stored as the `igdb` fact whenever a game is imported or matched – not refreshed and covers (TheGamesDB, ScreenScraper; image URLs reach the browser only as encrypted tokens, previews and downloads go through the server, allow-listed hosts only). **Integrations are configured in the app by admins** (`providers.Integration`, `services/integrations.DEFINITIONS`), not in `.env`; secrets are Fernet-encrypted with a key derived from `SECRET_KEY` and never sent back in clear text. All integrations are off by default. Sources never write catalog data themselves; `services/importer.py`, `services/facts.py` and `services/covers.py` do. Barcodes are only answered from our own data (`catalog.Barcode`, product codes): an unknown code goes to the title search and is stored once confirmed. See `docs/data-sources.md` before adding a source. Tests never hit the network (`apps/providers/tests/fakes.py`).
- Figures (amiibo) are works with `media_type=toy` on a platform of that media type.
- DVD/Blu-ray later: add platforms with `media_type=video`, a video metadata source (e.g. TMDB) implementing `MetadataSource`, and labels — the models already allow it.
- **Add-ons** — optional features kept in repositories of their own (private ones too) and copied into two git-ignored folders: `backend/addons/<name>/` (a Django app, installed unless `ADDONS_ENABLED=false`) and `frontend/src/addons/<name>/` (an `Addon` from its `index.ts`). They plug in only through the seams described in `backend/addons/__init__.py` and `frontend/src/addons/index.ts`: API routers, integrations, scheduler jobs, integration tests, `catalog.signals.work_merged`; routes, sidebar and user-menu links, head figures, game-page sections, integration sign-in flows. shelvd never names an add-on or its services; a new need gets a new generic seam. The committed OpenAPI schema is exported without add-ons. shelvd's checks also run over an installed add-on, its tests run in its own repo.

## Translations

- UI and server messages in German and English. Backend: source strings in English with `gettext`/`gettext_lazy`, translations in `backend/locale/de/LC_MESSAGES/django.po` (CI fails on untranslated or fuzzy entries; run `makemessages -l de --ignore=.venv`). Frontend: `vue-i18n`, common messages in `src/i18n/locales/`, each feature's in `src/features/<feature>/locales/{de,en}.json` under one namespace (merged automatically).

## Frontend design

- Explorer-like layout: sidebar (library switcher, saved views with their group tree, management links, upcoming, lists), topbar (search with `/`, add), main area (breadcrumb, nesting editor, folders, items in grid/list/table, status bar). Clicking a game opens its work page (`features/works`): cover, date with relative hint, details linking back into the explorer, the library's copies, all releases with tracking buttons.
- **One game page, three focuses** (`features/game`, `docs/concept-detail-page.md`): `/works/<id>` (Spiel), `/releases/<id>` (Ausgabe) and `/items/<id>` (Exemplar) are the same page (`GameView`), focused on the game, a release or a copy (`useGamePage`), plus `/edit` etc. below them. No library in game/release URLs – they show the current library's copies (`useCurrentLibrary`); a copy's page loads it by id (`GET /api/items/<id>`) and makes its library current (`openLibrary`). People don't think in levels, so the page hides them – no level trail, no level headings: `GameHead` (cover with franchises, series, developer and – not for the game – publisher below it; a kicker for release and game, none for a copy; title with the release number muted beside it; the game's description; a few figures), then sections in a fixed order, each folding in and out (`GameSection`, remembered per focus in the UI store, `useSections` holds the defaults): „Dieses Exemplar“ (`CopyFacts`, only with a copy; its actions in the heading), „In deiner Sammlung“ (`CopyShelf`: every copy of the game here, the opened one outlined; add a copy / watch), „Diese Ausgabe“ (`ReleaseFacts`, not for the game), „Das Spiel“ (`GameFacts`: first release, genres, modes, perspective, `LanguageTable`, play times, fact sources), „Alle Ausgaben“ (`ReleaseTimeline`: timeline and list), more of the series (`SeriesSection`) and „Weiterführend“ (`RelatedLinks`: the other focuses, external sources). Every piece of information shows on every focus that has it; the ⋮ menu holds the copy's, the release's and the game's actions for those who may. `DetailPage`/`DetailHero`/`HeroStats` also frame the term and platform pages.
- **No edit forms in modals.** Every create/edit form is its own route built with `components/app/EditPage.vue` + `EditSection.vue` (sticky Save/Cancel bar, `?back=` for catalog pages). Dialogs are only for confirmations; the add/scan flow and the fields and sort dialogs (`FieldsDialog`, `SortDialog`: display choices, not data) are the deliberate exceptions. Single-field inline changes (a status select) are fine.
- Three levels, always named and iconed the same (`LEVELS` in `lib/itemFields.ts`, `components/app/LevelHeading.vue`): **Spiel** (work, catalog), **Ausgabe** (release, catalog), **Exemplar** (item, this library). Never show the word "work" in the UI. Every field lives in `ITEM_FIELDS` (getter, formatting, choice labels); labels come from `useFieldLabel()`: a level's own fields read plainly ("Serie"), other objects as "Ort › Typ", an object's main field as just the object ("Plattform"). A view (`Overview`) stores per presentation which fields it shows (`fields.grid|list|table|detail`, empty = `DEFAULT_FIELDS`), its sort (up to five levels like `location.box,-release.number`, applied server-side) and its filters (conditions like `game.kind=game`, `game.title~A*`, `location.box?`, `release.year>=2020`, plus `match` all/any). Filters live only in the view, not in the page URL; unsaved field/sort/nesting changes do (`f_table`, `sort`, `g`). Table header clicks sort only in the page. Fields, sort and filter fields are picked from the same chooser (objects as clusters, search understands `ort.typ`).
- Dates of releases are shown with `components/app/ReleaseDate.vue` and edited with `DatePrecisionInput.vue` (`lib/releaseDate.ts` mirrors the backend's period logic). State that should survive reload/sharing lives in the URL query (see `features/explorer/composables/useExplorerState.ts`).
- Metadata labels in `font-mono text-[11px] uppercase tracking-wider text-muted-foreground`, counts in `tabular font-mono`, primary color only for the main action. Use `CoverImage` and `PlatformBadge` from `src/components/app`. Must work at 375 px.
- Permissions: `auth.isAdmin` / `auth.canContribute` (store), `can_edit` on games and releases, `canEdit(library.role)` for library content. Admin-only routes carry `meta.admin` (the router sends others to `forbidden`); edit pages that depend on an entry or a library role show `ForbiddenView` themselves. Never show a button that ends in „not allowed“.
- Clicking a copy in the explorer opens the copy's page (`/items/<id>`); with the detail column open it selects.
- Tests use `src/test/utils.ts` (`mockApi`, `renderApp`, `renderComponent`, `settle`; `testUser` is an admin, `plainUser` neither admin nor editor) and `src/test/fixtures.ts`.

## Docker / runtime

- The app container runs read-only, without capabilities, as an unprivileged user. Only `/data` (`DATA_DIR`, uploads etc.) and `/tmp` are writable — new features must write there, not loosen the hardening.
- supervisord runs gunicorn and nginx; nginx serves the SPA and proxies `/api` and `/admin`.
- `/admin` is closed in Docker unless `ADMIN_ENABLED=true`.
- Covers live in `/data/media` and nginx serves them under `/media/`. The SPA's CSP (`docker/security_headers.conf`) deliberately allows `'wasm-unsafe-eval'` (barcode decoder), `https://images.igdb.com` images (search previews) and the camera for our own origin — extend it the same deliberate way, never with wildcards.

## House defaults

Checked against django-spa-defaults 1.8.1 (2026-11-23).

- Releases: release-please
- Contributions: team only
- BE-11: met – `DEBUG` defaults to false (`env_bool("DEBUG", False)`), and `config/env.secret_key` refuses to start without a SECRET_KEY of 40+ characters unless DEBUG.
- BE-13: met – no mails or slow side effects run inside requests; the integrations' periodic work runs in `run_scheduler`.
- BE-14: met – writes with side effects (registration, deleting copies and libraries with their cover files, catalog merges) go through services; the remaining API writes save or delete the endpoint's own object only.
